# 身份验证器 · 技术方案 v1（纯技术）

> 出：MasterD(认知·三哥)
> 日期：2026-10-04
> 性质：技术方案（经 DeepSeek 多轮辩证）
> 范围：只谈技术+认知

---

## 一、核心结论（一句话）

> **别追求「意图可验证」，追求「越权不可发生」。**

| 概念 | 性质 | 能否做到 |
|---|---|---|
| 「意图可验证」（证明 agent 想干的=它干的） | 语义问题 | ❌ 无解 |
| 「越权不可发生」（任何动作都在授权内） | 集合包含问题 | ✅ 有解 |

**→ 工程边界画在「动作约束」，不画在「意图证明」。**

---

## 二、技术分层（按威胁模型）

| 层 | 内容 | 成熟度 |
|---|---|---|
| **密码学层** | 密钥、签名、nonce、防重放 | 🟢 成熟（商品化） |
| **信任锚层** | 公钥来源、可问责委托 | 🟡 难（治理+工程） |
| **语义层** | 意图验证 | 🔴 无成熟解 |

**关键认知：**
- 「信任锚」不是缺陷，是**地基**（任何系统都有不可再问的根）
- 真正该担心的是「**约束维度漏了**」，不是「根被信任了」

---

## 三、推荐架构（Capability 模型）

```
【核心原则】
资源方持有 root key；签发方只能「衰减」不能「扩权」；
约束在「资源方」独立验证；agent 完全不可信。

【流程】
1. 授权方（搭档/上级）签发 capability token
   · 内含约束：amount / target / action / 时限 / 次数 / 频率
2. Agent 拿着 token 请求动作
3. 资源方（服务器）独立验证：
   · token 是否有效（签名）
   · 动作是否在约束内（本地策略引擎，agent 改不了）
4. 通过 → 执行；不通过 → 拒绝
```

**参考实现：Macaroon（可衰减、不可扩权的授权令牌）**

## 四、五个「必须做」的模块

### 模块1：密钥与签名（密码学层）
```
· Ed25519 密钥对（每个 Agent 唯一）
· 私钥本地保管（优先硬件：TPM/SE；无则 OS keychain）
· 签名 payload = from|action|target|amount|nonce|ts
· 收方验签
```

### 模块2：防重放
```
· nonce（一次性随机数）+ 时间戳
· 收方维护「已见 nonce 去重表」
· 时间窗（超过 X 分钟的消息无效）
```

### 模块3：授权约束（Capability）★核心
```
· 授权 = 「动作集合」（不是「身份绑定」）
· 约束维度穷举：
  · amount（金额上限）
  · target（目标白名单）
  · action（允许的动作类型）
  · 时间窗（有效期）
  · 次数（最多几次）
  · 频率（每分钟最多几次）★容易被漏
· 约束在「资源方」验证（agent 侧不可信）
```

### 模块4：撤销与轮换
```
· 短期凭证（自动轮换）替代长期凭证
· 撤销列表（CRL）——但注意：agent 寿命可能短于撤销传播延迟
· 密钥轮换（定期 + 泄露时立即）
```

### 模块5：审计兜底
```
· 所有签名动作 → 落审计日志
· 即使约束漏了 → 事后可追溯、可止损
· 注意：审计不是安全，是止损
```

## 五、⚠️ 「做不到」的部分（诚实）

```
① 无法防「私钥被窃取后的冒充」（除非硬件级 + 无侧信道）
② 无法防「量子攻击」（除非后量子签名）
③ 无法防「agent 被注入后，在授权范围内作恶」
   —— 这是「约束维度没穷举」，补维度，不补"意图验证"
④ 无法证明「agent 的决策过程对应某个意图」（语义无解）
```

## 六、已知漏洞（DeepSeek 找我方案找出的）

**审我的身份证系统时找出的 7 个洞（本方案要避）：**
```
1. 自证陷阱（签名不证"是谁"）→ 用「可问责委托链」解
2. 地址重复（私钥越权持有）→ 私钥自持
3. 时间戳无约束 → 重放 → 用 nonce+去重解
4. 无撤销/轮换 → 加
5. 登记表本身没防篡改（最致命）→ 信任锚问题，要有可信根
6. 只验签名不验"地址属本家族" → 加白名单
7. 私钥存储环境没定义 → 强调"本地/硬件保管"
```

## 七、落地方案（分两层）

### 🟢 最小版（现在能做）
```
· Ed25519 密钥对（本地）
· 签名 + 验签
· nonce + 时间戳（防重放）
· 公钥表（登记 + 白名单）
· 轮换机制
→ 覆盖密码学层（成熟）
```

### 🟡 进阶版（需更多投入）
```
· Capability 模型（约束在资源方验证）
· 约束维度穷举
· 硬件密钥保护（TPM/HSM）
· 撤销列表
· 可问责委托链
→ 覆盖信任锚层（难）
```

### 🔴 语义层（当前无解）
```
· 意图验证
→ 不追（无解），用「约束 + 审计」替代
```

---

## 八、关键认知总结

```
1. 「身份验证」的密码学部分，已解决（用标准，不造轮子）
2. 真正难的是「信任锚」（治理+工程，不是纯技术）
3. 「意图可验证」语义无解 → 用「动作约束」替代
4. 工程上最累的是「约束维度穷举」（漏一个 = 一个洞）
5. 任何方案都有「天花板」（纯密码学防不了 prompt injection）

参考标准：IETF draft-klrc-aiagent-auth、SPIFFE/SPIRE、
         DIF KYA-OS、Macaroon、ERC-8004
```
